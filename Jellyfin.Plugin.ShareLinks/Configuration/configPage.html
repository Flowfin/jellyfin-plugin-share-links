Share Links

The address this server is reached at from outside, with no trailing slash, for example https://media.example.org, or https://example.org/jellyfin when a proxy puts the server under a path. Every share link is built from it.
While it is empty, the link is built from what the incoming request said the server was. That is a header, which is text whoever made the request wrote, so a request carrying a forged host produces a link pointing at somewhere else, which you then send to a guest. Set this value and the request is not consulted at all. Behind a reverse proxy it is the only reliable answer, because the address the proxy passes on is not the one the guest typed.
A value that is not an absolute http or https address is refused when a link is built, and no link is produced. It does not fall back to the request, because a typo here would then quietly restore the behaviour this setting exists to remove.
How many shares may be live at once. Live means neither revoked nor past its expiry, so revoking a share or letting one expire frees a place.
How many live shares may name the same item. Several is the ordinary case of one title lent to several people; this is the bound that keeps a loop pointed at one item from consuming the whole server ceiling.
Checked when a share is created and never when one is resolved, so lowering it leaves links you have already handed out alone.
A fallback rather than a second ceiling. It has to be at least one day and no longer than the ceiling above, because a default longer than the ceiling is a configuration in which every share created without an expiry is refused.
Counted from the instant the share stopped answering rather than from when it was created. Zero deletes it at the first write after that instant, which is how you empty the store of what has expired.
Leave it empty for no ceiling. Zero is refused rather than read as no ceiling, because serve nothing and serve without a limit are opposite instructions. Megabits per second here; the record keeps bits per second, which is the unit the account switch takes.
A ceiling on the account rather than on the share, so a guest invited to two shares carries one allowance across both rather than one each.

A value this plugin cannot work under is refused as it is saved and the message names the setting. Editing the configuration file by hand passes through none of that, and there the refusal arrives later, when the setting is next read.

The identifier of the one item being shared. This page does not look items up by title, for the same reason the table below names them by identifier: nothing here asks the server what an item is called.
One account is made per name, and the name is what appears in the server's own user list. A name that is already taken is refused and nothing is made.
Read in this browser's time zone and sent as an absolute instant. Leave it empty to take the default lifetime above.

The link and the credentials below are shown once. The server keeps only a keyed hash of the token and writes no credential down, so it cannot produce either of them again, and leaving this page or creating another share is the end of them. Copy them now.

Guest Credential

Each guest signs in on the server's own sign-in page with the name and credential beside it, and then opens the link. A guest who opens the link before signing in is sent to the sign-in page and opens the link again afterwards; nothing here carries the destination across.

Shares

Every share the server holds, including the ones that have stopped working. A share that expired and a share that was never made look the same to somebody who is only told what is live, so the state column is what keeps them apart.

This page enforces nothing. Everything it offers is checked again on the server, and everything it hides is still reachable by anybody who can call the routes. The revoke button appears only on a share that is still live, because pressing it on one that has already stopped changes nothing; that is the server's rule and not this page's, and a second press is accepted and leaves the first press's instant, reason and revoker where they were.

The keyed hash secret

The server keeps one secret and every share link is checked against it. Replacing it is what to reach for when the secret itself may have leaked: a copy of the data folder in the wrong hands, a backup restored somewhere it should not have been, or a support bundle that turned out to include it. To stop one link that went to the wrong person, revoke that share instead.

Pressing this stops every live share on this server at once, and there is no way back. Every link that has been handed out stops working, every share in the table above is marked revoked, and the guests this plugin made for them are signed out and disabled. No link can be reissued, because only a keyed hash of each token was ever written down.

The count above is read from the table when this page last loaded it, so it is what was live then rather than what is live at the moment of the press. The number the server answers with is the one taken as the shares were stopped, and that is the one to believe.

What is not here. The link is not, and cannot be: only the keyed hash of a token is written down, so the server cannot produce a link a second time even when asked, and the table above is a listing rather than a way back to what a create answered. The item is named by its identifier rather than by its title, because the listing answers with the identifier and nothing here asks the server for a title. The ceiling column is the share's own, which is the number that was typed onto this share. The in-force column is what a guest of it would actually be held to, one line per invited account, with the ceiling that produced it named beside the number: Share is this share's own, Account is that guest's own remote client limit, and ServerRemoteClientLimit is the server-wide one. Where two of them sit at the same value both are named, because lowering the one that was not named would look like a change that did nothing. An invited account this plugin did not create is not confined by it either, so no ceiling of this plugin's reaches that account and the line says so rather than showing a number.

Each line of the in-force column also says whether that ceiling can be met for this item, and it says so only where there is something to say. NOTHING CAN BE SERVED is the one that needs an operator: every version the server offers is above the ceiling and none of them can be brought under it, so a guest opening this link is refused rather than served at a lower quality, and the repair is to raise the ceiling or to share something the server can serve under it. met only by transcoding is not a fault and is a cost, because the server re-encodes rather than sending the file as it is. not known is a question the server did not answer, most often an item it reports no bitrate for, and it is neither of the other two. A line with nothing after the number is a ceiling a version of this item already fits under.

The in-force column is read at the instant the listing was, in the same way the state column is. The ceiling a guest actually meets is worked out again when they ask to play something, out of the same three values as they stand then, so a value somebody moves in between is a disagreement between this page and the server rather than a fault in either.
